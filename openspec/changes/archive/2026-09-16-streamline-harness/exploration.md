# Exploration: streamline-harness

## Project Type

**Web testing**: not-web

This repository (`archon-ai`) is a Go CLI/TUI harness with no browser surface, no
`package.json`, no web framework, and no existing E2E tooling. Playwright remains
disabled (`playwright.enabled: false` in `.archon/config.yaml`). The project type
is confirmed `not-web`; group E does not apply to this change.

---

## Current State — Overview

The harness is composed of:

- **Go binary** (`cmd/archon/`): `init`, `update`, `config`, `status`, `map`, `route` subcommands.
- **Config** (`internal/config/config.go`): strongly-typed YAML struct with structs for
  `MutationTesting`, `Judge`, `Playwright`, `Security`, `Impeccable`, `Graphify`, `Models`.
- **TUI** (`internal/tui/model.go` + eight tab files): 8 tabs — Agent, Models, Judge,
  Mutation Testing, Playwright, Security, Impeccable, Graphify.
- **Init templates** (`internal/initcmd/templates.go`): static Go string consts that emit
  CLAUDE.md / AGENTS.md with the full 7-group preflight ceremony.
- **Skills** (`skills/`): 24+ embedded SKILL.md files covering all SDD phases plus
  harness-specific concerns.
- **Phase state machine** (`skills/harness-workflow/SKILL.md` +
  `openspec/specs/harness-workflow/spec.md`): one-direction linear sequence, no skip
  allowed.

## Concern 1: Preflight Simplification

### Current surface map

The 7-group preflight lives exclusively in two places:

| File | Location | Content |
|---|---|---|
| `internal/initcmd/templates.go` | `orchestratorSections` const, lines 56–109 | Full 7-group arrow-key questions (A–G), hard-gate rules, mapping paragraphs for E/F/G |
| `CLAUDE.md` (repo root) | "SDD Session Preflight" section | Rendered copy of the above — emitted by `RenderClaudeMD` |
| `AGENTS.md` (repo root) | Same section | Rendered copy via `RenderAgentsMD` |

`templates.go` is the **single source of truth**. Both `CLAUDE.md` and `AGENTS.md` are
rendered outputs (regenerated by `archon init` or `archon tui` save). Editing
`templates.go` automatically fixes both orchestrator files.

The current hard-gate rules say: "ask all seven groups every SDD session." There is
no per-change override mechanism; there is no way to suppress the ceremony when a
user has a session-level default they want silently applied.

The engram group (B2/B3) is baked into the same const, so removing it requires
editing `orchestratorSections` in `templates.go`.

Graphify (G) and Impeccable (F) groups are in the same const (lines 83–103) plus two
"mapping paragraph" sentences after them.

The preflight "HARD GATE" rules live at lines 105–110 of `orchestratorSections`.

#### Mapping paragraph locations (templates.go)
- Group E mapping paragraph: lines 91–93 (`playwright.enabled`)
- Group F mapping paragraph: lines 94–97 (`impeccable.enabled`) — REMOVE with Impeccable
- Group G mapping paragraph: lines 98–103 (`graphify.enabled`) — REMOVE with Graphify

#### The `orchestratorRulesClaude` and `orchestratorRulesOpencode` consts
- Rules 7–9 (lines 194–198 in Claude; 207–212 in Opencode) reference playwright,
  impeccable, and graphify respectively. Rules 8 and 9 are removed with Impeccable
  and Graphify. Rule 7 (playwright) stays.
- `templates_test.go` asserts on preflight group strings (lines 149–155) — all
  F/G/engram assertions must be removed or updated.

#### "Propose a different preflight when warranted" — mechanical options

Three approaches exist:

**Option A — Config-driven defaults, session override only when delta exists.**
Store the standard defaults in `.archon/config.yaml` (e.g. `preflight.rhythm:
interactive`, `preflight.pr_strategy: ask-chained`, `preflight.review_budget: 800`).
The orchestrator reads them silently at session start, skips the ceremony entirely,
and only asks a focused question when a specific change's risk profile warrants a
different value (e.g. "This change looks large — suggest switching to 400-line budget,
confirm?"). This is the recommended path because it makes the defaults machine-readable
and visible in `archon status` / `archon tui`.

**Option B — Single session-open question.**
Replace the 7-group cascade with one question: "Usar configuración estándar o
ajustar?" — where "estándar" maps to the fixed defaults listed above. A "ajustar"
answer opens only the groups the user wants to change. Lower ceremony, no config
file changes needed, but defaults are not visible outside a running session.

**Option C — Remove preflight entirely; bake decisions into skills.**
Remove the preflight block from CLAUDE.md. Encode the standard defaults directly
into the skills (e.g. `harness-workflow` enforces interactive mode; `sdd-tasks`
defaults to chained strategy when estimate > 800 lines). The orchestrator announces
its decisions rather than asking. Highest agility, lowest escape hatch — a per-change
override requires skill edits.

Recommendation: Option A, because it preserves auditability and a clean UX path for
the "harness proposes a different preflight" case (the config becomes the source of
truth, and the orchestrator's question is scoped to a delta from it, not a full
re-ceremony).

## Concern 4: Simplify Judge Flow

### Current orchestration map

The judge flow has four layers:

1. **`harness-judge` skill** (`skills/harness-judge/SKILL.md`): The orchestrator-facing
   gate. Step 2 delegates to the `archon-judge` subagent, which internally calls
   `judgment-day`. Steps 3/3b/3c run optional quality gates. Steps 5–6 run the
   auto-re-apply loop (up to 3 retries).

2. **`judgment-day` skill** (`skills/judgment-day/SKILL.md`): The dual-adversarial
   review skill. Launches Judge A and Judge B in parallel (two blind sub-agents),
   synthesizes findings, asks before fixing, and re-judges. It is a standalone skill
   invocable independently of SDD.

3. **`archon-judge` subagent** (`AGENTS.md` / `.claude/agents/` phase files): The
   hard-gate model wrapper. `harness-judge` delegates to it; it invokes `judgment-day`
   internally.

4. **`harness-workflow` spec** (`openspec/specs/harness-workflow/spec.md`): The state
   machine that calls `judge` as a mandatory phase after `verify`, before `archive`.

The dual-review within `judgment-day` is the core complexity: two judges in parallel,
synthesis, classification of confirmed/suspect/contradictions, optional fix round, and
re-judge. This is appropriate for opt-in adversarial use — it is over-engineered as a
mandatory SDD-path step.

### What "single judge" means mechanically

The SDD path should call one judge agent (the existing `archon-judge`, using the
Opus model) that performs a single coherent review against spec compliance, design
coherence, and code quality — returning a verdict (pass/fail + issues). No parallel
launch, no synthesis across two judges, no blind-review ceremony.

The `judgment-day` skill stays as-is but becomes **opt-in only**, triggered when the
user explicitly says "juzgar", "dual review", or equivalent — not by the SDD pipeline.

Changes required:

| File | Change |
|---|---|
| `skills/harness-judge/SKILL.md` | Replace Step 2 "Delegate Dual Review" with a single-judge review against spec/design/code criteria. Remove dual-review language. Keep Steps 3/3b/3c quality gates (conditional). Keep re-apply loop (Step 6). |
| `skills/harness-judge/SKILL.md` | Remove delegation to `archon-judge` as a wrapper around `judgment-day`; instead, `harness-judge` IS the review orchestrator — it reads code and spec, applies the criteria, and returns a verdict. OR keep `archon-judge` as the single reviewer with a focused system prompt. |
| `skills/judgment-day/SKILL.md` | Remove any language implying it is called automatically by the SDD pipeline. Keep the standalone activation contract ("Load only when user explicitly asks…" — this language already exists). |
| `openspec/specs/harness-judge/spec.md` | Update to reflect single-judge model. |
| `CLAUDE.md` / `AGENTS.md` | Rule 6: update to remove "invoke harness-judge" if harness-judge collapses into the orchestrator, OR keep as-is if harness-judge remains as the single-step wrapper. |

The `archon-judge` subagent can remain as the model-gated runner; the change is that
it performs a focused single review rather than orchestrating two blind agents.

`config.yaml` → `judge.enabled` already supports disabling the phase entirely —
this flag requires no change.

## Concern 5: New Lightweight Bug-Fix SDD Flow

### Current state-machine gate

`skills/harness-workflow/SKILL.md` line 62: "NEVER allow a transition that skips a
mandatory phase." The `PHASE_ORDER` array (line 92 of the SKILL) is hard-coded as
`[explore, propose, spec, design, tasks, apply, verify, judge, archive]`. The
spec (`openspec/specs/harness-workflow/spec.md` line 61) names propose, spec,
design, tasks, apply, and verify as mandatory — propose through verify are
non-skippable by design.

There is no current concept of an alternate or abbreviated track. Every change must
traverse all nine phases; there is no `type` field on `state.yaml` to signal a
different flow.

### What a bug-fix fast path needs

Proposed abbreviated track: `explore → spec (scoped) → apply → verify → archive`
(skipping propose, design, tasks, judge).

The gates to bypass or keep:

| Phase | Status in fast path | Rationale |
|---|---|---|
| propose | Skip | Bug fixes don't need a proposal: the fix is self-evident |
| spec | Keep (scoped) | A minimal delta spec grounds the apply step |
| design | Skip | Bug fixes usually have one obvious solution |
| tasks | Skip | Single-unit changes don't need decomposition |
| apply | Keep | Mandatory — code change |
| verify | Keep | Mandatory — correctness check |
| judge | Skip | Manual verification sufficient; can be opt-in |
| archive | Keep | Mandatory — state management |

#### Mechanically required changes

1. **`state.yaml`** needs a `track` field: `full` (default) or `bugfix`. The
   harness-workflow skill reads `track` to select the appropriate phase sequence.
2. **`skills/harness-workflow/SKILL.md`** needs an alternate `PHASE_ORDER` for the
   `bugfix` track:
   `[explore, spec, apply, verify, archive]`
   and the same state-machine enforcement (no skipping within the track, but the track
   itself determines which phases are mandatory).
3. **`openspec/specs/harness-workflow/spec.md`** needs a "Phase Tracks" requirement
   section with Gherkin scenarios for the bugfix track.
4. **`CLAUDE.md` / `AGENTS.md`** (and templates.go) needs a brief note that the
   orchestrator can start a bugfix track by setting `track: bugfix` in the change
   init, and the Vague Request Guard should distinguish bug reports from feature
   requests to auto-select the track.
5. **`sdd-init`** (skill, not Go code) needs to accept a `track` parameter.
6. **`sdd-spec`** in bugfix track must be told to produce a "scoped spec" (delta only,
   no full Gherkin suite required — minimal acceptance criteria).

The judge skip in bugfix track is reconciled with `judge.enabled` in config: if
`judge.enabled: true` AND track is `bugfix`, the judge phase is advisory (opt-in per
session) rather than mandatory. Alternatively, bugfix track simply omits judge from
its `PHASE_ORDER`.

#### Risk: Human Review Gate in fast path

The Human Review Gate (CLAUDE.md) currently fires after propose, spec, design, and
tasks. In the bugfix track, it fires after spec only (the only artifact-producing
phase before apply). This is simpler but still requires the gate to fire.

## Concern 6: Agile-Flow Ideas — Prioritized

### Hotspot 1: Preflight ceremony (highest friction, easiest fix)

**Evidence**: `internal/initcmd/templates.go` lines 56–110 — 7 arrow-key questions
asked every session, even when the user always picks the same options.

**Idea**: Config-driven session defaults (see Concern 1 Option A). When the session
defaults are set, the preflight reduces to a one-line "Using standard defaults —
[interactive / openspec / ask-chained / 800 lines]. Confirm or adjust?" The harness
proposes different preflight values only when a specific change's estimate triggers a
threshold (e.g. estimate > 800 lines → "suggest switching to review budget 400").

**Files**: `internal/initcmd/templates.go` (orchestratorSections), `internal/config/config.go`
(new `Preflight` struct), `CLAUDE.md`.

### Hotspot 2: Engram multi-branch in every phase skill

**Evidence**: Every phase SKILL.md has 3–4 engram/hybrid/none branches (e.g.
`sdd-apply/SKILL.md` lines 41, 49, 51, 98, 132, 230). This doubles the cognitive
load of reading a skill and creates dead branches that are never exercised (engram is
not used in this project).

**Idea**: Remove engram entirely from skills (Concern 3). Each phase skill becomes
~30% shorter and unambiguous — there is exactly one persistence path.

**Files**: All phase skills + `_shared/persistence-contract.md` + `_shared/engram-convention.md`.

### Hotspot 3: Dual-judge complexity in SDD path

**Evidence**: `skills/harness-judge/SKILL.md` Step 2 delegates to `archon-judge`,
which calls `judgment-day`, which launches two parallel blind agents, synthesizes
across them, asks before fixing, and re-judges. All of this is inside what is supposed
to be a single automated quality gate.

**Idea**: Single judge (Concern 4). The `judgment-day` skill's dual-adversarial
ceremony is excellent for a deliberate human-triggered review ("juzgar") but adds
unnecessary latency and complexity to the routine automated judge phase after verify.
A single focused review with the same retry loop is sufficient for the SDD path.

**Files**: `skills/harness-judge/SKILL.md`.

### Hotspot 4: Impeccable + Graphify in every phase skill

**Evidence**: Every phase SKILL.md has conditional blocks for both Impeccable and
Graphify that are skipped when disabled (which is always, in practice). The
`harness-judge` skill has ~40 lines dedicated to the Impeccable detection gate.

**Idea**: Remove Impeccable and Graphify from skills (Concern 2). Skills become
significantly cleaner. If these features are ever re-added externally, they can be
maintained as separate overlay skill files rather than baked into the core phase skills.

**Files**: See Concern 2 enumeration.

### Hotspot 5: Rigid linear phase machine (no bug-fix track)

**Evidence**: `skills/harness-workflow/SKILL.md` line 62 — "NEVER allow a transition
that skips a mandatory phase." The `PHASE_ORDER` is a single hard-coded 9-phase
sequence.

**Idea**: Bug-fix track (Concern 5). A `track: bugfix` state in `state.yaml` selects
a 5-phase sequence. The harness-workflow skill branches on `track` before building the
transition table. Effort: Medium.

**Files**: `skills/harness-workflow/SKILL.md`, `openspec/specs/harness-workflow/spec.md`,
`_shared/persistence-contract.md` (state.yaml format), CLAUDE.md template.

### Hotspot 6: Human Review Gate fires for every artifact-phase

**Evidence**: CLAUDE.md "Human Review Gate" requires a pause after propose, spec,
design, and tasks — four mandatory pauses per change regardless of change size.

**Idea**: In interactive mode, gate is always active (no change). In the bug-fix
track, gate fires once (after scoped spec). This is a natural consequence of Concern 5
rather than a standalone change. No new config knob needed.

### Hotspot 7: `archon route` as a mandatory dependency

**Evidence**: `orchestratorRulesClaude` rule 2 requires `archon route` before every
phase delegation. This is a Go binary call that adds a round-trip on every phase
start. If the binary is absent or the route classification is uncertain, the
orchestrator must invoke the `sdd-router` classifier.

**Idea** (low priority): The `archon route` step is valuable for preventing
misrouting on ambiguous messages, but it adds friction for experienced users who know
which phase they want. Consider making it advisory ("route result: explore — proceed?")
rather than a hard prerequisite. Low risk because this is a classification aid, not a
gate.

## Open Questions and Risks

### Preflight (Concern 1)

1. **Where do session defaults live?** If in `config.yaml`, a new `Preflight` struct
   is needed (Go code change + Clone + CloneRoundtrip + TUI tab or config set). If
   only in the CLAUDE.md instructions, no Go code is needed but defaults are not
   machine-readable.
2. **"Harness proposes a different preflight when warranted" — trigger criteria?**
   Who decides when the change warrants a different choice? Options: estimate-based
   (harness computes line estimate after tasks and proposes a budget change), or
   explicit orchestrator judgment during propose. The former requires the harness to
   have a line-count forecast; the latter is pure CLAUDE.md instruction prose.
3. **Back-compat**: Existing `CLAUDE.md` files in consumer projects were generated
   with 7 groups. After this change, `archon update` will regenerate them. Any project
   that has customized its `CLAUDE.md` past the generated template will need to merge.

### Engram removal (Concern 3)

4. **`sdd-onboard` and `sdd-init` skills** have engram-mode paths for initial project
   onboarding. Do consumers of the harness who use engram today expect it to keep
   working? The requirement says "remove engram from scope" — treat as a breaking
   change for engram users (none known in this repo).
5. **`_shared/persistence-contract.md`** is referenced by every phase skill. Simplifying
   it to openspec-only effectively removes `none` mode as well. Confirm whether `none`
   (return result only, no artifacts) should be preserved.

### Impeccable / Graphify removal (Concern 2)

6. **`skills/embed_test.go`** lists `"graphify"` as an expected embedded skill
   (line 29) but does NOT list `"impeccable"`. After removal, `graphify` must be
   removed from the expected list too, and `skills/graphify/SKILL.md` directory
   must be deleted. The `skill_count` in `CLAUDE.md` drops by 2 (impeccable + graphify),
   but since `skill_count` is generated dynamically from the embedded FS, the count
   auto-corrects on `archon init` / `archon update`.
7. **`openspec/specs/graphify-integration/spec.md`** is a live (non-archived) spec.
   It should be archived as part of this change (or deleted — it describes a feature
   being removed).
8. **`ImpeccableTab` enum removal** shifts `GraphifyTab` index by -1 and `tabCount`
   by -2 (both removed). The `model_test.go` ShiftTab-from-AgentTab test (line 109–
   122) currently expects `GraphifyTab` as the last tab. After both removals, the last
   tab will be `SecurityTab` — this test must be updated.

### Judge simplification (Concern 4)

9. **`archon-judge` subagent identity**: Currently `harness-judge` delegates to
   `archon-judge` which wraps `judgment-day`. After simplification, `archon-judge`
   should be a single-pass code reviewer. What are its exact review criteria?
   (spec compliance, design coherence, code quality — same as today but without the
   dual-synthesis ceremony.) This needs to be specified in the propose/spec phases.
10. **`judgment-day` standalone trigger**: The skill already has a tight activation
    contract ("Load only when user explicitly asks…"). This is sufficient to prevent
    automatic invocation. No code change to `judgment-day` itself is needed — only
    the `harness-judge` skill needs to stop calling it automatically.

### Bug-fix fast path (Concern 5)

11. **`state.yaml` schema change**: Adding `track` is a backward-compatible addition
    (absent field defaults to `full`). Existing in-flight changes are unaffected.
12. **Scoped spec format**: What is a "scoped spec" for a bug fix? A minimal set of
    acceptance criteria without full Gherkin? This must be defined precisely in the
    spec phase or the `sdd-spec` skill risks producing a full spec anyway.
13. **When does the orchestrator offer the bug-fix track?** Recommend: during the Vague
    Request Guard — if the user describes a bug (not a feature), the orchestrator asks
    "¿Es un bug o una nueva funcionalidad?" and routes accordingly.
14. **Judge is skipped in bug-fix track but `judge.enabled: true` in config**: The
    config flag controls the full track. In the bug-fix track, judge should be opt-in
    per session, not config-gated. This needs a clear rule in harness-workflow.
